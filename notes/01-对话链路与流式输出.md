# 从裸 HTTP 到 ChatClient：一次对话请求到底走了哪些层

写 AI 应用最容易犯的错，是把它当成"调一个 HTTP 接口"。真按这个思路做，代码会迅速退化成一堆手拼 JSON 的字符串：换模型要改请求体、加历史要改 payload、要流式要自己解析 `data:` 行、要审计要在每个入口复制粘贴日志。Spring AI 的价值不在于"帮你发包"，而在于它把 AI 调用拆成了一条有扩展点的链路：**模型能力（ChatModel）→ 会话门面（ChatClient）→ 提示词（Prompt）→ 调用链（Advisor）→ 结果（ChatResponse / Stream）**。搞清楚这条链，后面所有"工程化"才有落点。

## 两个对象：ChatModel 管能力，ChatClient 管会话

`ChatModel` 是最薄的一层，只回答一件事：给一个 `Prompt`，还一个 `ChatResponse`。同步是 `call()`，流式是 `stream()` 返回 `Flux<ChatResponse>`。它不关心历史、不关心提示词长什么样，甚至不关心你把它用在哪。本项目里 `ChatClientConfig` 只做了一件事——用自动配置注入的 `OpenAiChatModel` 建一个 `ChatClient` 单例。

`ChatClient` 才是业务真正打交道的门面。它提供链式语法：`.prompt()` 起手，`.options()` 定本次调用的模型参数，`.user()` 塞用户输入，`.advisors()` 挂拦截器，最后 `.call()` 或 `.stream()` 收口。它比 `ChatModel` 多出来的东西，恰好就是工程化需要的：会话级默认值（系统提示词、默认 advisor）、提示词模板、结构化输出转换、以及 advisor 链。

这里有个容易被忽略的取舍。项目里 `ChatController` 每次请求都 `ChatClient.create(openAiChatModel)` 新建一个客户端，而不是注入那个单例 Bean。原因是每个请求要带自己的模型名、温度值和不同的 advisor 组合。但更干净的做法是**注入单例、用 `mutate()` 派生子客户端**：`chatClient.mutate().defaultOptions(...)` 只做浅拷贝，比从 `ChatModel` 重建一遍要轻，语义也更明确——派生体继承基础配置，只覆盖差异项。每次 `create` 的问题不在性能，而在于它悄悄丢掉了单例上可能挂载的公共配置（比如全局默认系统提示词），一旦以后要统一加，就得改所有 `create` 的位置。

## 模型与温度为什么放在请求级

`OpenAiChatOptions` 挂在 `.options()` 上，意味着模型名、温度是**每次调用**决定的，不是启动时写死的。这是"多模型共存"的实现方式：一个 `OpenAiChatModel`（一套 base-url + api-key）可以对多个模型名发请求，前端下拉框选什么，后端就传什么。如果按模型建 `ChatModel` Bean，模型一多就是一串配置类。

温度值 0.0 在客服链路上有实际意义：检索增强的场景要求"照着资料说"，随机性只会带来改写和臆造。而创意类场景（起名、写文案）才需要 0.7 以上。同一套代码，温度是配置项而不是常量，这是可调参的前提。

有个细节值得记住：**`ChatClientRequest` 被 Advisor 改造时，`options` 必须显式带走**。`CustomerServiceAdvisor` 里重建请求用的是 `ChatClientRequest.builder().prompt(newPrompt).build()`，而 `newPrompt` 是通过 `DEFAULT_PROMPT_TEMPLATE.create(vars, chatClientRequest.prompt().getOptions())` 生成的——第二个参数就是在保 `options`。漏了它，模型名和温度会退回默认值，表现为"前端选了 A 模型，实际跑的是默认模型"，且不报错。这类 bug 只能靠日志里打出实际请求的 model 才能发现。

## 流式响应有两条通道，而且第二条是累积值

流式的正文很好理解：模型一个字一个字往外吐，每个 chunk 的 `getText()` 是**增量**。麻烦的是推理模型（DeepSeek-R1 类）多出来的 `reasoningContent`——Spring AI 2.0.1 把它放在 `AssistantMessage.getMetadata().get("reasoningContent")` 里，而且给的是**从流开始到当前的完整推理文本**，不是本帧增量。

这个不一致直接决定了前端会不会重复显示。项目里的处理是记录"已下发长度"，只截取新增部分：

```java
int[] reasoningLen = {0};
String reasoningContent = message.getMetadata().get("reasoningContent").toString();
if (reasoningContent.length() > reasoningLen[0]) {
    String delta = reasoningContent.substring(reasoningLen[0]);
    reasoningLen[0] = reasoningContent.length();
    return AIResponse.builder().reasoning(delta).build();
}
return AIResponse.builder().v(text).build();
```

`int[]` 是为了在 lambda 里改值——Java 的闭包只能捕获 final 变量，数组引用是 final、元素可变，这是最轻的绕过方式。同一套逻辑在 `CustomStreamLoggerAndMessage2DBAdvisor` 里又写了一遍，用于把完整推理落库。

另一处必须知道的差异：`getResult() == null` 的 chunk 要跳过。有些帧只带元数据（结束标记、用量统计），直接取 `getResult().getOutput()` 会 NPE。

## SSE 落地：为什么前端不用 EventSource

后端接口声明 `produces = MediaType.TEXT_EVENT_STREAM_VALUE`，返回 `Flux<AIResponse>`，Spring MVC 会用 `ReactiveTypeHandler` 把每个元素按 `data: ...\n\n` 写出，浏览器侧就是标准的 Server-Sent Events。

但浏览器的原生 `EventSource` 只支持 GET，无法携带 JSON 请求体（用户消息可能有几千字）。所以前端用的是 `@microsoft/fetch-event-source`——它用 `fetch` 拿到 `ReadableStream`，自己按 SSE 协议解析，天然支持 POST + body，还能带自定义 header。这是"接口设计成 POST 却仍用 SSE"的常见解法。

两个部署期的坑，跟代码无关但一定会踩：一是 Nginx 默认 `proxy_buffering on`，会把流攒在网关，表现为"最后一次性吐出来"；二是 `Content-Encoding: gzip` 对 SSE 同样有害，压缩缓冲会让流式失效。上线时要显式关掉这两个。

## 这一层的边界

到这里链路只能"聊"：能流式输出、能选模型、能带系统提示词。缺的是三样东西——上下文记忆（每次请求都是新的会话）、知识边界（模型不知道你的私有资料）、外部信息（模型不知道今天发生了什么）。这三件事都不该塞进 Controller，它们是**调用链上的横切关注点**，也就是下一层的 Advisor。
